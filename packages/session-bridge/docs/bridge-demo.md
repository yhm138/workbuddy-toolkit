# 会话桥自检：两个 WorkBuddy 会话之间真实往返

这不是示意图，是一次真实执行的实录。命令：

```bash
node bin/dsh2wb.mjs bridge-test --wait 20000 --timeout 150000
```

它做了什么：在指定工作区**新开一个 WorkBuddy 会话**，向它提问，等它回答；再把它的会话 ID
告诉它，要求原样回显。两轮都拿到完整回复，才算双向通信成立。

## 结果

| 项 | 值 |
| --- | --- |
| 发起方 | 当前会话（CLI 进程） |
| 新会话 | `a1b2c3d4-0001-4a00-8000-000000000001` |
| 工作区 | `D:/your/project` |
| 第 1 轮耗时 | 约 10 秒 |
| 第 2 轮耗时 | 约 13 秒 |

**第 1 轮回答**（问：工作目录 / UTC+8 时间 / 会话 ID）：

```json
{"cwd":"D:/your/project","utc8":"2026-10-24T11:49:23+08:00","sid":null}
```

`cwd` 对了，`utc8` 与投递时刻对得上，`sid` 是 `null` —— **agent 看不到自己的会话 ID**。
这正是会话桥存在的理由：ID 只在宿主与本地记录里，模型自己拿不到，得由桥喂给它。

**第 2 轮回答**（把 ID 告诉它，要求回显）：

```json
{"echo_sid":"a1b2c3d4-0001-4a00-8000-000000000001","ok":true}
```

回显的 ID 与宿主分配的一致 —— 闭环。

## 三重证据

同一件事从三个互相独立的地方读到，内容一致：

1. **宿主快照** —— `requestsWb` 走宿主通道 `wb:conversations:requests` 读回；
2. **CLI 结果** —— `.probe/bridge-test.json`；
3. **本地落盘** —— `~/.workbuddy/projects/<项目>/<会话>.jsonl`，即下面这份回放。
